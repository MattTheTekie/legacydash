# 0.35.0-alpha / receiver-name deep link and floating pet

Open receiver setup now builds Settings, finds the existing DLNA receiver group/name editor, focuses that field and requests that its rectangle be scrolled into view. The same route is used by idle/active receiver-setup entry; incoming-cast presentation still opens the cast player directly through its existing presenter code. It does not force a keyboard-open command, save an unfinished name or stop an active cast merely by navigating. Applying a changed name retains its separate confirmation.

PersonalActivity removes the old full-width pet footer as it is created, reclaiming its reserved 56dp. The application attaches one transparent 104x96dp floating pet to each app-owned activity content frame, above the dashboard/media/colouring/kiosk content. It defaults to the lower-right with a small margin and can be dragged within that activity's bounds to uncover controls. Positions are per-view, not persisted across activity recreation. Touches outside the small pet view are not intercepted by a full-screen overlay. Tapping opens a compact care menu rather than navigating away from media.

The existing pet.dock preference controls visibility; its pet-page checkbox label now describes a floating companion. Hide in the care menu switches off that same preference; re-enable from the existing pet page. All overlay instances and the dashboard pet page share the app's existing PetState/storage model so care actions do not compete through stale separate models. The drawing retains the existing egg/companion forms, stages, colours and reactions, with no theme inversion. Animation stops on pause/window hiding/detachment, and preference listeners are unregistered on detach.

A layout observer only ensures overlay attachment/order after setContentView and clamps its position on resize. It does not change fullscreen flags or use viewport-size keyboard polling; the prior focus-based fullscreen controller remains. The overlay uses ordinary app content views, not SYSTEM_ALERT_WINDOW, a foreground overlay service, lock-task mode or display-over-other-apps permission. It cannot cover system UI, keyboards, external apps or separate dialog windows. Vendor/legacy surface composition can still affect how overlays appear over media. No build or device test was run.

Verify CI, reclaimed footer space, direct Settings name navigation/scroll, all activity transitions, media surfaces, drawing gestures near the pet, drag/tap/accessibility behavior, hide/re-enable and state persistence, rotation, fullscreen stability and lifecycle cleanup.
