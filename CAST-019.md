# 0.19.0-alpha / automatic fullscreen casting

Receiver discovery/playback remains service-owned and enabled by the existing preference. The launcher now uses AutoCastActivity, which removes Cast receiver buttons from normal screens. Settings retains a single background-receiving switch and a trusted-LAN warning. The required foreground-service notification and Disable action remain; the old CastPanel class is retained for source compatibility but is no longer the active casting UI.

An incoming Play command requests a separate fullscreen CastPlayerActivity rather than requiring a receiver dashboard. A weak presenter reference allows automatic opening while legacydash is visible, and the current school note is flushed first; failed school saves block automatic takeover. A finger-down drawing gesture defers takeover until the gesture ends. Opening a separate activity retains the previous workspace; existing pause hooks checkpoint artwork and pause other app playback.

On Android 10+ this implementation does not attempt an unsolicited activity launch when no app presenter is visible; the user taps the receiver notification. Older Android receives a best-effort automatic launch, subject to device policy. It does not request overlay privileges, full-screen notification privileges, lockscreen bypasses or background-launch exemptions. Screen-off/unlock/other-app interruption is not guaranteed.

The dedicated player uses a hardware-accelerated TextureView and explicit Surface attachment/detachment, without app sidebar, pet, seasonal overlay or receiver warning panel above the media. It fits the reported video dimensions inside the viewport without stretching. Controls reveal on touch and hide during playback; first hidden-controls touch is consumed on DOWN, and seeking/finger-down prevents the hide timer. Back hides the viewer without disabling receiving or stopping audio; Stop stops the media. Back marks that media generation dismissed to prevent immediate automatic reopening. Remote Stop/completion exits the viewer.

The service tracks video dimensions, video tracks and first-frame rendering, uses AudioAttributes on API21+, and uses the URL data-source overload directly for network media. Player errors expose numeric what/extra codes and a short reason in the viewer and LegacyDashCast logs, without logging the full media URL. Video track with no rendered frame shows a compatibility hint, not a false claim that playback is working.

This does not add software video decoders or receiver-side transcoding and cannot make all MP4 files supported. MP4 may contain H.264, HEVC, AV1, different profiles/bit depths, audio tracks and resolutions that a particular Android decoder cannot play. Sender-side transcoding may still be needed; H.264 Baseline/AAC at modest resolution is compatibility guidance, not a guarantee. The actual problematic MP4 codec has not been identified from a sample/log.

No local Android compilation or device/network playback test was performed. Verify CI, TextureView output and aspect ratio, API17 rendering callbacks, supported/incompatible MP4s, audio-only playback, photos, remote Play before preparation, Stop/Back/reopen, background notification behavior, rotation and workspace restoration. Existing LAN/no-pairing and codec/device limitations remain.
